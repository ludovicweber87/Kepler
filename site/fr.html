Kepler 1.0 · local-first · macOS

Le cockpit d'une flotte d'agents IA.

Un agent, un terminal, une branche — vous travaillez donc encore en série. Kepler donne à chaque agent Claude son propre worktree git, une persona réutilisable et le contexte GitHub dont il a besoin, puis vous renvoie en direct tout ce qu'il fait.

Pas de cloud. Pas de compte. Aucune clé API à gérer — l'accès GitHub vient de votre session gh locale.

Les cinq piliers de la 1.0

Pensé pour la façon dont le travail se passe vraiment.

01

Une flotte, pas un agent.

Chaque session a son worktree isolé dans .worktrees/, sa branche et son terminal — donc N agents travaillent en même temps sans jamais se marcher dessus. La sidebar est votre vue de flotte : projets → worktrees → sessions, avec une pastille sur tout agent qui vous attend.

  • Nouveau worktree, sur une branche neuve
  • La branche courante, telle quelle
  • Une branche existante, locale ou distante
  • Mode libre — sans projet, juste un agent dans un dossier

02

Des personas qui portent vos conventions.

Arrêtez de vous répéter. Une persona regroupe un nom, un rôle, un system prompt et ses propres réglages de modèle, effort de raisonnement, mode de permission et couleur d'accent — puis pilote chaque session lancée avec elle.

  • Rattachées à certains repos, ou globales
  • Changement de persona en cours de conversation — sans redémarrage, sans perte de contexte
  • Le composer prend la couleur de la persona : vous savez toujours à qui vous parlez

03

Des docs avec qui discuter.

Décrivez un sujet, choisissez une source — connaissance générale ou l'un de vos repos — un niveau, une longueur, un format et un angle optionnel. Un agent rédacteur produit la doc en Markdown, en arrière-plan.

Et surtout : chaque doc a son propre chat, côte à côte avec le texte. Posez une question sur le sujet, ou demandez une modification — l'agent édite le document sur place via des outils in-process encadrés. Édition par correspondance exacte uniquement ; les demandes ambiguës sont refusées plutôt que devinées.

04

Branché sur GitHub, pas greffé dessus.

Lancez un agent directement depuis une issue. Kepler injecte le titre et le corps de l'issue dans le system prompt de la session, lie la session à l'issue, crée la branche et le worktree, et poste un commentaire sur l'issue pour que la trace soit visible sur GitHub. L'agent démarre en sachant déjà pourquoi il est là.

  • Kanban Projects V2 — drag-and-drop, statuts synchronisés en GraphQL, cache local pour un affichage instantané
  • Toutes vos PRs ouvertes avec leur CI et le merge en un clic
  • Des issues rédigées par l'IA à partir d'une phrase
  • Triage post-merge — l'issue passe en colonne QA, le worktree est archivé

05

Le daily s'écrit tout seul.

Un calendrier mensuel de comptes-rendus quotidiens rédigés par l'IA, par repository. Kepler collecte l'activité réelle de la journée — commits sur toutes les branches, pull requests, logs d'activité des agents — et la fait synthétiser par un agent en quelques puces à la première personne.

Les cellules affichent les points en clair. Un clic ouvre le rapport complet et la timeline d'activité brute qui l'a produit. Générez, régénérez ou supprimez n'importe quel jour.

Tout le reste

Le reste du cockpit.

◱ Le Workbench

La conversation de l'agent à gauche ; Changes, Activity, Issue, Explorer et Reader à droite ; plusieurs onglets de terminal en dessous (⌘J) sur un split redimensionnable. Les fichiers s'ouvrent en onglets à côté du chat.

◈ De vraies sessions SDK

Les agents tournent via le Claude Agent SDK, streamés en WebSocket : cartes de tool call, demandes de permission validées depuis l'UI, questions inline. Les transcripts font autorité côté serveur, en SQLite, et se rejouent à la reconnexion.

◷ Timeline d'activité

Une timeline lisible dérivée du flux d'events — décisions, fichiers modifiés, commits, blocages, et un récapitulatif final. Plus un recap par session quand le travail est terminé.

◔ Notifications

En SSE : quand un agent termine, échoue ou se retrouve bloqué en attente de vous, une notification priorisée et dédupliquée arrive instantanément — avec un son et une notification système si vous êtes parti.

◫ Des sessions qui survivent

Fermez l'onglet, redémarrez la machine, revenez : la conversation, le terminal et le worktree sont toujours là. Le label de session est découplé de git — et un renommage manuel gagne toujours sur le titre automatique.

⇅ Issues, PRs, tâches

Un kanban synchronisé avec Projects V2, chaque PR ouverte avec ses checks, et des tâches avec échéance, couleur d'urgence, épinglage, et un lien vers une issue GitHub — ou la création d'une nouvelle.

⌘ Scripts par repo

Déclarez des commandes par repo et retrouvez-les en boutons dans la barre du haut. Chacune tourne dans un nouvel onglet terminal ou comme message envoyé à l'agent.

⚙ Réglages par repo

Prompts personnalisés de création de PR et de commit & push, fichiers à copier dans chaque nouveau worktree, scripts de setup et d'archivage, et la colonne QA utilisée par le triage post-merge.

◐ À votre main

Sept thèmes plus une palette entièrement personnalisable, polices et tailles indépendantes pour l'app et le terminal, cinq langues d'interface, et un clic pour ouvrir un worktree dans votre éditeur.

Démarrer

Deux commandes et un nouveau terminal.

  1. Installer

    curl -fsSL https://raw.githubusercontent.com/ludovicweber87/Kepler/main/install.sh | bash

    Clone une copie dédiée dans ~/.kepler/repo, la build, et place une commande kepler stable dans votre PATH. Rejouable — la relancer met à jour sur place.

  2. Chargez votre PATH, puis démarrez

    source ~/.zshrc && kepler start && kepler seed

    L'installeur ajoute ~/.kepler/bin à votre PATH, mais le shell depuis lequel vous l'avez lancé ne le sait pas encore — d'où le source (un nouveau terminal fait le même travail). Remplacez par ~/.bashrc ou ~/.config/fish/config.fish selon votre shell — l'installeur affiche la commande exacte en fin d'exécution.

    start démarre le serveur agent, l'app web et la fenêtre desktop. seed installe la bibliothèque de personas. L'accès GitHub vient de votre gh session — il n'y a rien d'autre à configurer.

  3. Les cinq premières minutes

    Indiquez un repo à Kepler dans Settings, connectez un board Project V2, puis cliquez + sur un projet, choisissez une persona et un mode de lancement. Collez l'URL d'une issue GitHub au lancement pour donner à l'agent tout son contexte.

Prérequis

  • macOS — développé et testé dessus
  • Node 20–25 — les modules natifs ne sont pas encore sur 26
  • gh, authentifié (gh auth login)
  • claude CLI dans votre PATH
  • tmux et git

État runtime

La base SQLite, les pids et les logs vivent dans ~/.kepler/ et survivent aux mises à jour. Les overrides optionnels vont dans ~/.kepler/.env.

Le CLI

kepler start
Build si besoin, lance, ouvre la fenêtre
kepler stop
Arrête l'agent, l'app web et la fenêtre
kepler restart
Stop puis start — applique une mise à jour
kepler status
Chaque service, avec son pid et son URL
kepler logs
Suit tous les logs, ou un service
kepler update
Récupère main, réinstalle, rebuild
kepler seed
Installe les personas de départ
